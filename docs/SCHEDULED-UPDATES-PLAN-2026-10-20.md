CommDDL 定时更新、管理员邮箱与发布前审阅执行计划
================================================

编制日期：2026-10-20（Asia/Shanghai）。交接对象：**commddl-执行**。

本文件是执行计划。本轮仅完成方案与交接文件；业务代码、邮箱配置、邮件发送、定时任务和远程发布均留给执行阶段。

**预期结果**：CommDDL 定时检查官方来源，按信息缺口补采官网详情、当届征稿和日期变化，生成可比较、可取舍的候选更新；向用户自行添加的管理员邮箱发出审阅提醒；管理员确认最终变更后，系统自行提交、检查并更新正式目录、网页及订阅日历。**日常运行不需要打开 Codex、唤醒 Agent、手工改 YAML 或找 Agent 上传。**

本文将“推送前”落实为“合入 main、公开发布及更新订阅日历之前”。候选内容可以先进入专用分支和草稿 PR 供审阅。定时采集任务没有发布权限；发布服务只能在管理员明确批准最终版本、检查通过且仓库规则允许后，自动合并对应 PR 并触发部署。

二、实现路线与组件职责
----------------------

继续使用 YAML 作为**审核通过后的版本化发布源**，由系统根据已批准候选生成增量修改。要替换的是一次性人工提取流程，而非为了定时更新迁移全部目录到数据库。

建议执行基线：GitHub Actions 负责采集和检查；小型管理服务采用 Cloudflare Worker + D1，负责邮箱配置、采集状态、候选批次和发信记录；主站仍由 GitHub Pages 发布。D1 可通过 Worker 绑定访问，密钥通过服务端 Secrets 保存，能力依据见 [D1 文档](https://developers.cloudflare.com/d1/worker-api/) 和 [Workers Secrets 文档](https://developers.cloudflare.com/workers/configuration/secrets/)。这是建议方案，尚未部署，也不假定项目已有相关账号。

| 组件 | 职责 |
|---|---|
| Pages 主站 | 浏览目录、显示已审阅官网分段、提供“管理员通知设置”入口 |
| 独立管理页面与 API | GitHub 身份验证、项目权限校验、邮箱管理、批次逐项审阅、修改和批准发布、通知记录；管理页面和 API 同源部署，减少跨站登录问题 |
| D1 私有表 | 保存项目、管理员收件人、验证记录、来源状态、候选批次、邮件投递与审计记录；不存入公开 YAML |
| 定时采集任务 | 读取受控来源、按需扩展官方子页面、形成结构化候选与来源证据 |
| GitHub 草稿 PR 与发布服务 | 系统生成正式数据提交并运行检查；管理页显示最终差异，通过 GitHub API 留下真实管理员批准记录，再在规则满足后自动合并；GitHub 页面作为可追溯入口和备用操作入口 |
| 邮件适配器 | 服务端发送验证邮件、测试邮件、更新审阅提醒与必要故障提醒 |

邮件适配器先定义统一接口，再按项目已有资源接入一家服务。若没有现有通道，可采用 Resend HTTPS API；其生产发送需要自有且已验证的发信域名，不能把 qq.com 当作项目发信域名。没有发信域名时，执行者应保留接口并接入项目所有者已有的 SMTP/邮件服务，不要求其为了本功能先购买域名。[Resend 发信域名要求](https://resend.com/docs/dashboard/domains/introduction)

**将 Agent 目前的职责固化为产品能力：**

| 现在由 Agent 完成 | 上线后由谁完成 |
|---|---|
| 打开网页并寻找相关信息 | 受来源清单控制的抓取器、标题树解析器和站点适配器 |
| 整理字段和判断属于哪届会议 | 有 schema 的归一化程序、年份/身份/轮次规则；含糊结果进入待审状态 |
| 找到变化并决定修改哪些文件 | 持久快照、三方差异引擎及管理员页面上的逐项决策 |
| 手写 YAML 和变更记录 | 确定性的补丁生成器，维护稳定 ID、revision 和 history |
| 提交、上传、发 PR | GitHub App 调用受控接口；不依赖本机 Git 和聊天指令 |
| 测试、构建、发布 | CI 和受审核门禁约束的发布服务，失败保留旧版 |

首次为来源配置抓取规则、处理站点改版和改进解析器，仍属于软件维护，可由人或开发 Agent 协助；常规更新本身必须独立运行。首版不把大模型调用设为必要依赖，也不把“定时启动一个 Agent 去浏览官网”作为实现。对已登记来源稳定自动更新；陌生来源、结构改版和语义不明必须显式暴露缺口，不能声称通用解析器能正确处理任意官网。

新增来源的管理操作应能选择已有适配器、指定页面/章节映射、试抓取并预览；缺少新解析能力时才进入开发维护。动态页面使用部署在采集任务中的浏览器程序，不依赖用户桌面的浏览器或 Codex 会话。

三、邮箱添加入口与真实发信
--------------------------

主站页脚或管理菜单增加“管理员通知设置”，打开独立管理页面。普通访客继续直接浏览目录；管理页面通过 GitHub 登录，并在服务端检查目标仓库权限。首版仅允许仓库管理员维护收件人；若要授权其他维护者，使用由管理员管理的明确名单。**填写邮箱本身不会授予仓库审核权。** GitHub 可查询用户对指定仓库的权限，不能只相信前端传来的角色。[GitHub 仓库权限接口](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user)

用户可添加多个收件邮箱，查看“待验证 / 已启用 / 已停用 / 发送失败”，重发验证、启停、删除以及发送测试邮件。1319630151@qq.com 是用户最初提供的可添加地址；不写入代码、不预设为所有部署的固定收件人，也不在本轮替用户注册或发送验证邮件。

邮箱必须由后端持久保存，换浏览器、换电脑和无人值守运行后仍生效。邮箱和验证令牌不得进入公开仓库、构建数据、日历、离线 HTML 或日志。只在管理界面向有权限的人展示；公开摘要掩码显示。

| 接口草案 | 行为 |
|---|---|
| GET /admin/recipients | 返回当前项目的收件列表与状态，要求管理权限 |
| POST /admin/recipients | 添加邮箱并发送验证邮件；对项目内重复地址去重 |
| POST /admin/recipients/:id/resend-verification | 限频重发验证邮件 |
| POST /admin/recipients/:id/verify | 校验有期限的一次性令牌，确认邮箱归属；验证令牌只保存摘要 |
| PATCH /admin/recipients/:id | 启用或停用，未验证地址不能启用 |
| DELETE /admin/recipients/:id | 删除收件配置，并清理相应验证记录 |
| POST /admin/recipients/:id/test | 向已验证的该邮箱发送一封明确标识的测试邮件 |
| GET /admin/update-batches/:id | 显示来源、旧值/新值、缺口、最终预览和检查进度 |
| PUT /admin/update-batches/:id/decisions | 保存逐项接受、拒绝、纠正；自动生成该决策版本的 YAML 补丁、分支和检查任务 |
| POST /admin/update-batches/:id/approve-publish | 对已展示的最终 head SHA 明确批准并请求发布；要求审核权限与防重复提交 |
| POST /internal/update-batches/:id/notify | 供可信工作流请求通知；后端自行读取收件人，不接受工作流任意指定 to |

验证链接的 GET 只展示确认页，实际确认使用 POST，避免邮件安全扫描直接完成操作。邮箱验证与测试发送按项目、操作者和地址限频。退出登录、权限失效及无权访问其他项目均须有明确反馈。

内部工作流调用使用服务端校验的凭据和防重放机制，例如签名、时间戳和唯一请求号。浏览器不能持有邮件密钥、GitHub 机器人私钥或内部调用密钥。

收件人为空、全部停用或发送配置缺失时，采集仍可生成候选，但批次停在“通知配置待完成”，不能被标记为可发布。设置页给出具体修复入口，不能假装已经提醒管理员。

四、按需采集与结构化内容
------------------------

先建立来源清单，区分期刊/会议系列、具体届次、轮次、专题和来源版本。优先读取已有 url、sourceUrl、authorGuideUrl、cfpUrl，再从正文链接发现官方子页面。会议系列介绍进入 venues；当届 CFP、时间线、地点和投稿规则进入 calls；不得把下一届覆盖到旧届次，也不得把主会与 workshop、demo、short paper 混为一项。

| 触发条件 | 补采内容 |
|---|---|
| 尚无官网分段或简介明显不足 | 官网介绍、范围、主题、相关主要章节与来源标题 |
| 投稿入口或稿件类型缺失 | Author Guidelines、Submission、Publication 页面；页数、格式、匿名要求、投稿系统等明确规则 |
| 临近截止、日期未知或出现延期标记 | 当届 Important Dates、CFP、Author Timeline；摘要前置、全文、通知、终稿、时区及延期原文 |
| 官网出现新届次、新轮次或新专题链接 | 校验年份、母载体和投稿类别，生成新 call 候选；不复用旧 call ID |
| 地点、举办时间或投稿状态发生变化 | 补读官方详情并记录前后差异；不把举办日期当作截稿日期 |
| 首页没有正文、入口跳转或来源失效 | 检查受控子页；按已批准站点适配器读取动态页面/PDF，仍无法取得则记缺口 |
| 索引、分区或评级来源有新版本 | 进入单独的版本核对任务，保留体系、年份、ISSN 与证据；不从首页宣传语自动赋级 |

采集策略采用“正文结构发现 + 类别映射 + 站点适配器”。保留 h1—h6 的标题层级、原始标题与顺序；识别明确的 role=heading 和已知站点的自定义标题容器。按同级/上级标题和 DOM 容器确定分段边界，支持段落、嵌套列表、表格和必要链接，避免父子段落、列表和表格单元格重复计入。

标题类别应覆盖 General Information、About、Aims and Scope、Related Topics、Topics of Interest、Call for Papers、Important Dates、Submission Guidelines、Paper Categories、Publication 等，并支持中文对应。其他与投稿决策有关的大标题也进入候选，不因不在两个固定标题集合内而丢弃。菜单、页脚、Cookie、广告和赞助导航不作为正文。

先解析静态 HTML；确属动态加载且需要补齐的站点，再启用受限浏览器适配器；PDF 来源使用专门文本/表格适配器，证据保留页码。不能读取的来源明确标记“待适配/待人工核对”，不得算作成功，也不得以已有主题标签冒充官网原文。

每个载体默认最多扩展 6 个页面、链接深度 2，跨域仅允许已核实的出版方、学会或投稿系统域名。超出预算时记录未读链接和缺口，供下一批或人工补齐；不进行全站无边界爬取。保留公开 HTTPS、重定向、超时、体积与地址校验，对最终实际连接及每次重定向都做检查。

官网长文在候选中保留可复核的结构和必要证据。公开页保存投稿所需事实、主题和适量摘要；不默认整页复制受版权保护的长文。任何删节都有 truncated/省略说明及原文入口，不继续使用当前无提示的 8 项、1200 字符截断。

五、候选模型、差异和人工审阅
----------------------------

扩展 officialSections 时兼容当前 heading/content/items/sourceUrl/verifiedAt。新结构至少支持稳定 sectionId、parentId、headingLevel、order、来源锚点，以及类型化 blocks（paragraph、list、table、links）。blocks 为新格式的唯一正文来源；渲染器先读 blocks，旧格式作为兼容路径，避免同一内容显示两遍。venues 和 calls 都应支持各自的官网分段。

sectionId 由来源、稳定锚点/章节身份和人工映射确定，不能直接采用正文 hash，否则每次修改都会变成“新增分段”。标题改名和重复标题要按来源、层级和位置匹配，不能再使用“同标题全部跳过”。

维护候选另存 fetchedAt、extractorVersion、sourceHash、contentHash、来源选择器/锚点、候选状态和审批记录。fetchedAt 表示采集时间；verifiedAt 表示人工核对时间。现有脚本“提取成功即写 verifiedAt”的行为必须改掉。日常复查无内容变化不批量刷新正式 YAML 日期。

采用三方比较：上次已批准来源快照、当前正式 YAML、此次官网候选。只产生新增、正文修改、标题/层级调整、日期变化、新征稿、疑似删除、来源失效等有意义差异。忽略空白、菜单顺序、跟踪参数和页面生成时间等噪声。人工改写与官网同时变化时形成冲突，保留人工内容，交给管理员取舍。

来源抓取失败、章节突然消失、空页面或解析结果为零，不自动删除已发布内容。明确删除也先作为审阅候选。管理员可以拒绝某一候选并记录原因；来源内容没有新变化时，不每天重复提交同一个被拒建议。

为适配现有校验规则，**未经人审的已知日期和分段先存在候选模型，不直接伪装为 verified 的正式 YAML**。管理员在管理页查看来源和差异、逐项接受/拒绝或纠正后，服务端保存决策，自动调用 apply 模块生成对应 YAML 并填写实际核对信息。系统创建候选提交并运行检查；页面展示该提交的最终内容，管理员点击“批准并发布”后，系统合并该版本并部署，不再改动批准内容。对候选摘要的选择不能替代对最终内容的确认。

拟新增内部命令名称，供 CI、管理服务及开发诊断使用，**不是管理员日常操作步骤**。网页保存决策后由服务端生成决策文件并自动调用，不能让管理员下载文件后找 Agent 执行：

    npm run update:collect -- --due
    npm run update:collect -- --ids ofc,twc --dry-run
    npm run update:plan -- --batch <batch-id>
    npm run update:apply -- --batch <batch-id> --decisions <review-decisions.json>

apply 只接受与当前 base SHA、来源内容指纹相符的决策，先生成临时结果、校验完整目录再原子写回，不能半途写坏源数据。日期修改保持 call/node ID，增加 revision 并追加 history；新届次使用新 ID；仅日期不补时区，明确时刻才保存偏移与原始时区。

候选预览、补丁生成和最终检查必须使用同一版本的确定性转换程序。审批后不再重新自由整理文本或重新抓取并替换数据；若来源或转换结果变化，生成新版本并重新审阅。发布任务中不得嵌入“让 Agent 根据需要调整数据”的步骤。

六、定时策略与无人值守状态
--------------------------

先以以下可配置值落地，运行一周后根据变更量和站点负载调整。推荐北京时间每天 07:17、13:17、19:17、次日 01:17 调度，UTC 表达式为 17 5,11,17,23 * * *。每次只处理到期项，不代表每 6 小时抓取所有网站。

| 来源类别 | 默认复查间隔 |
|---|---|
| 未来 30 天内截止的有效征稿、延期和当前冲突 | 每 6 小时 |
| 其他仍有效的征稿和活跃专题 | 每日 |
| 期刊/会议系列介绍、主题、作者指南 | 每周；有缺口时提前补采 |
| 已过期届次 | 截止后 7 天复查一次，之后每月或手动 |
| 评级和索引来源 | 每月发现版本；新版本进入独立证据核对 |

提供 workflow_dispatch，支持指定 ID、仅重试失败项和 dry-run。首次补齐分批处理当前目录，并单列历史参考，不一次向管理员提交数百条不可阅读的变化。默认每批最多 20 个实体，紧急日期变化优先；具体预算与频率均放在受控配置中。

调度状态持久保存在后端，至少区分 lastAttemptAt、lastSuccessfulFetchAt、nextCheckAt、lastFetchedHash、lastPublishedHash、重试次数和待审批次。采集成功不能提前推进已发布基线。Actions cache 只作加速，不是唯一状态源。ETag/Last-Modified 可减少下载；304 只有在对应快照确实存在时才可复用。

全局并发默认 3，同一域名串行并限频，429/网络错误指数退避；个别来源失败不阻断其他采集，但整批必须报告失败覆盖面。任务使用 concurrency 防止重入，同一候选通过项目、实体和内容指纹去重。待审分支已有人工修改时停止自动覆盖，保留下一批候选。

GitHub 定时任务运行在默认分支，可能延迟；公开仓库长期无活动还可能停用调度。因此管理页需显示最后成功运行时间，提供手动补跑与故障提示，不承诺准点服务，也不能靠同一个未运行的定时任务自报停用。[GitHub schedule 规则](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

七、邮件提醒和发布门禁
----------------------

端到端顺序：**定时采集 → 持久候选 → 邮件提醒 → 管理员在网页取舍 → 系统生成正式 YAML 和 PR、完成检查 → 网页展示最终差异 → 管理员批准并发布 → 系统合并 main、构建部署并记录结果**。未操作、超时、未读邮件或没有回复，一律不视为批准。

邮件包含项目、批次、变化数量、关键前后值、临近截止与冲突、采集失败、原始来源、候选预览、最终差异入口、PR 地址和当前版本标识。纯文本与 HTML 内容一致，提供“前往审阅”，不提供匿名点击即合并。收件人逐个发送，不通过 To/CC 泄露其他管理员邮箱。

邮件状态区分 queued、sending、sent、delivered、failed/bounced。服务商接受发送并返回消息 ID 才记 sent；sent 不等于已读。使用数据库 outbox、唯一键和服务商幂等键，按“批次版本 + 收件人 + 邮件类型”去重，失败只重试未成功的收件人。Resend 的幂等窗口为 24 小时，跨日去重仍由项目自己的记录负责。[Resend 幂等规则](https://resend.com/docs/dashboard/emails/idempotency-keys)

每个批次版本记录启用收件人快照和通知结果。默认所有该版本收件人均须取得 sent 记录；部分发送失败则标记不完整，不能静默跳过。管理员可修复地址后重试，或明确停用失败地址并重新确认通知名单。没有实质变化不发更新提醒；长期待审可合并为低频催审，不重复轰炸。

新增可信 review-gate，将 final head SHA、数据差异 hash、决策版本、通知版本和审核者身份绑定。自动提交、人工编辑、重新生成或影响最终内容的基线变化都会使旧批准失效，重新检查并确认最新版本。正式 YAML 转换若只完成已通知并批准的候选，也必须展示最终差异；出现额外实质变化时重新发提醒。

仓库保护要求：main 必须经 PR，要求项目指定审核者批准和全部必要检查通过；机器人无绕过权；启用新提交撤销旧批准。用 CODEOWNERS/维护者名单将审核权映射到 GitHub 身份，不能从 QQ 邮箱猜测账号。[GitHub 分支审阅保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging)

实现管理页“批准并发布”时，使用管理员明确授权的 GitHub App 用户访问令牌，对最终 commit_id 创建管理员本人的批准记录；机器人安装令牌只负责创建数据 PR 和在规则满足后合并，不能自审代替管理员。合并请求必须传入预期 head SHA，遇到新提交、权限变化、检查失败或保护规则不满足就停止并回显原因。用户令牌失效时重新登录，不要求用户找 Agent 登录或上传。[GitHub 审阅 API](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request)、[GitHub 合并 API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)

修改 pages.yml：上传正式发布产物和 deploy 都限定 refs/heads/main，并只允许已经通过检查的可信发布事件；github-pages 环境同样限制 main。草稿 PR 预览使用独立产物，不能写正式 Pages 或订阅日历。手动从候选分支运行工作流必须验证为无法部署。

机器人优先采用项目安装的 GitHub App 令牌，以便分支和 PR 事件按预期触发检查。若复用 GITHUB_TOKEN，需要明确处理其事件限制：当前官方规则下，机器人创建/更新的 PR 检查可能等待人工批准运行，普通机器人 push 也不能视为已触发后续工作流。批准“运行工作流”与批准“数据内容”是两步，不能混用。[GitHub 工作流触发规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)

采集任务没有发布权限；通知密钥只交给可信通知步骤；不从候选分支执行拥有服务端密钥的代码。必要门禁不能通过 skipped/neutral 或缺失检查伪装为通过。部署失败时保留此前在线版本，回滚通过恢复上一份已审核数据或重新部署已知合格主分支版本完成。

实现阶段运行 npm run check、npm test、npm run build，新增测试必须加入实际 test 命令；后端另做持久化迁移、权限与邮件集成验证。测试以冻结 HTML/PDF 文本夹具为主，真实站点用于受控验收，避免把外站不稳定变成常规测试失败。

完成条件是一次可复核的真实闭环：用户添加并验证邮箱 → 关闭本地电脑/Codex 后定时程序抓到官网真实变化 → 邮件提醒 → 管理员在网页查看、取舍并批准最终修改 → 系统自动合并发布 → 页面及日历更新；再验证一轮无变化运行不会产生新数据提交或重复提醒。不得由 Agent 代替任何一个日常运行步骤来通过验收。真实接入尚未完成时，交付状态必须写“本地已实现 / 外部配置待完成”，不能以模拟邮件和空分段宣称功能完成。

外部接入清单由执行者准备为具体可操作的配置步骤：主仓库管理权限、GitHub App/身份验证配置、管理服务及数据库、邮件通道凭据（或已验证发信域名）、公开管理入口 URL、GitHub 仓库保护和 Secrets。现阶段不读取或索要密码。权限暂缺时先完成所有本地实现和验证，再明确列出仅需所有者完成的配置动作。
